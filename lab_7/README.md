# Лабораторная работа № 7

## 1. Цель работы

Объединить результаты лабораторных работ № 1–6 в один законченный проект базы данных маркетплейса: собрать полную схему, согласованные данные, аналитические запросы и представления, серверную логику, JSONB-атрибуты, индексы и документацию, достаточную для защиты проекта.

Проект должен показывать не отдельные разрозненные запросы, а работающую базу данных целиком: от создания таблиц и ограничений целостности до оптимизации конкретных запросов и обоснования принятых решений.

## 3. Запуск проекта

Требуется PostgreSQL 14+ (проект проверен на PostgreSQL 18.6).

```bash
createdb marketplace
psql -d marketplace -f lab_7/sql/run_all.sql
```

Либо по отдельности:

```bash
psql -d marketplace -f lab_7/sql/01_schema.sql
psql -d marketplace -f lab_7/sql/02_seed.sql
psql -d marketplace -f lab_7/sql/03_views.sql
psql -d marketplace -f lab_7/sql/04_functions_triggers.sql
psql -d marketplace -f lab_7/sql/05_optimization.sql
psql -d marketplace -f lab_7/sql/06_queries.sql
```

`run_all.sql` использует `\ir`, поэтому пути к файлам разрешаются относительно самого скрипта. Запускать его можно из любого каталога:

```bash
psql -d marketplace -f /полный/путь/lab_7/sql/run_all.sql
```

**Важно:** `01_schema.sql` пересоздаёт таблицы проекта и удаляет прежние данные маркетплейса в текущей базе. Скрипт можно запускать повторно: он начинает с `DROP TABLE ... CASCADE`, затем создаёт схему заново. Для чистой демонстрации лучше использовать отдельную базу.

## 4. Описание схемы базы данных

### 4.1. Состав схемы

В проекте 14 таблиц:

| Группа | Таблицы | Назначение |
|---|---|---|
| Пользователи | `users`, `sellers`, `addresses` | Профили, магазины продавцов, адреса доставки |
| Каталог | `categories`, `products`, `stock` | Категории, товары, остатки на складе |
| Корзина | `carts`, `cart_items` | Корзина пользователя и её позиции |
| Заказы | `orders`, `order_items` | Заказы и их состав |
| Платежи и доставка | `payments`, `deliveries` | Оплата и доставка заказов |
| Обратная связь | `reviews` | Отзывы и оценки товаров |
| Служебная | `product_price_audit` | История изменения цен |

Основные связи:

- `users` → `sellers` — 1:0..1, связь через `sellers.user_id` с ограничением `UNIQUE`;
- `users` → `addresses`, `carts`, `orders`, `reviews` — 1:N;
- `sellers` → `products` — 1:N;
- `categories` → `products` — 1:N;
- `categories` → `categories` — самоссылка через `parent_id` (иерархия);
- `products` → `stock` — 1:0..1;
- `products` → `cart_items`, `order_items`, `reviews` — 1:N;
- `carts` → `cart_items` — 1:N;
- `orders` → `order_items` — 1:N;
- `orders` → `payments`, `deliveries` — 1:0..1 (ограничение `UNIQUE` по `order_id`);
- `addresses` → `deliveries` — 1:N.

### 4.2. Соответствие третьей нормальной форме

Реляционная часть схемы находится в 3НФ:

1. **1НФ.** Все скалярные столбцы содержат атомарные значения; повторяющихся групп нет. Позиции заказа и корзины вынесены в отдельные таблицы `order_items` и `cart_items`.
2. **2НФ.** В таблицах с составными первичными ключами (`order_items(order_id, product_id)`, `cart_items(cart_id, product_id)`) неключевые столбцы зависят от всего ключа, а не от его части.
3. **3НФ.** Нет транзитивных зависимостей: название категории и имя продавца не дублируются в `products`, а хранятся в `categories` и `sellers`; адрес не дублируется в `orders`; характеристики товара не дублируются в строках заказа.

Осознанные отступления от «чистой» 3НФ:

- `products.attributes` типа `JSONB` — полуструктурированные характеристики (цвет, память, вес и т.д.). Разные категории имеют разный набор свойств, поэтому JSONB удобнее набора разреженных столбцов или EAV-таблицы. Это не повторяющаяся группа, но формально выходит за рамки классической реляционной модели.
- `products.rating` — агрегат по `reviews`, хранится для быстрого чтения и поддерживается триггером.
- `orders.total_amount` — снимок суммы заказа на момент оформления. Он не пересчитывается при каждом чтении и сохраняет историческую стоимость даже при изменении цен товаров.
- `order_items.unit_price` — снимок цены товара на момент заказа; специально не ссылается на текущую `products.price`.

Такая денормализация контролируемая: агрегаты и снимки не должны обновляться вручную, за них отвечают функция `place_order` и триггеры.

## 6. Наполнение данными

Скрипт `02_seed.sql` создаёт согласованный набор данных через `generate_series`, поэтому результат воспроизводим.

| Таблица | Количество после `02_seed.sql` |
|---|---:|
| `users` | 100 |
| `sellers` | 10 |
| `categories` | 10 |
| `products` | 1000 |
| `stock` | 1000 |
| `addresses` | 100 |
| `carts` | 100 |
| `cart_items` | 500 |
| `orders` | 1000 |
| `order_items` | 1000 |
| `payments` | 1000 |
| `deliveries` | 1000 |
| `reviews` | 1000 |
| `product_price_audit` | 0 |

После демонстрационных вызовов в `04_functions_triggers.sql` добавляются два заказа, две позиции заказа и один отзыв; в аудите появляется одна запись об изменении цены. Итоговые количества после полного прогона: `orders` — 1002, `order_items` — 1002, `reviews` — 1001, `product_price_audit` — 1.

Особенности наполнения:

- пользователи 1–10 имеют роль `seller`, пользователи 11–100 — `customer`;
- каждый продавец владеет 100 товарами; каждая категория содержит 100 товаров;
- остаток товара с `id = 7` равен 17;
- цена товара с `id = 7` равна 1459.00, после демонстрации аудита — 1559.00;
- средняя оценка товара с `id = 7` после демонстрации — 4.00;
- категории 6–10 вложены в категории 1–5 через `parent_id`;
- всем 1000 товарам заполнено поле `attributes` (цвет, память, вес и т.п.);
- даты заказов распределены по 14 дням:

```sql
UPDATE orders
SET created_at = CURRENT_DATE - (((id - 1) % 14)::int * INTERVAL '1 day');
```

Это нужно потому, что `orders.created_at` по умолчанию равен `now()`: без распределения все 1000 заказов попали бы на одну дату, и аналитика «по дням» стала бы вырожденной.

## 7. Перечень реализованных запросов

Все запросы находятся в `sql/06_queries.sql`; ключевые запросы лабораторных № 3 и № 4 вошли в итоговый набор, часть из них объединена и переработана для сквозного проекта.

| № | Тема | Что показывает |
|---:|---|---|
| 1 | `JOIN` трёх таблиц | Каталог: товар + категория + продавец |
| 2 | `LEFT JOIN` | Покупатели без собственного магазина (90 человек) |
| 3 | `GROUP BY` + `HAVING` | Продавцы с выручкой больше 1 030 000 (6 продавцов) |
| 4 | Скалярный подзапрос | Товары дороже средней цены |
| 5 | Подзапрос с `IN` | Товары, которые хотя бы раз заказывали (1000) |
| 6 | Подзапрос с `EXISTS` | Продавцы, у которых есть товары (10) |
| 7 | CTE (`WITH`) | Выручка по категориям |
| 8 | Рекурсивный CTE | Дерево категорий: 5 корневых и 5 вложенных |
| 9 | `ROW_NUMBER`, `RANK`, `DENSE_RANK` | Рейтинг товаров по цене внутри категории |
| 10 | `SUM() OVER (ORDER BY ...)` | Накопительная выручка по дням |
| 11 | `LAG`, `LEAD` | Выручка предыдущего/следующего дня и изменение |
| 12 | `SUM() OVER (PARTITION BY ...)` | Доля товара в выручке своей категории |
| 13 | `->` | Извлечение JSONB-значения как `jsonb` |
| 14 | `->>` | Извлечение JSONB-значения как текста |
| 15 | `@>` | Проверка вхождения JSONB (`color = black`) |
| 16 | `?` | Проверка наличия ключа (`memory`) |
| 17 | Запросы к VIEW | Готовые отчёты по продавцам, категориям, товарам и статусам заказов |

Для компактности вывода в демонстрационных запросах используется `LIMIT`; сами аналитические конструкции от этого не меняются.

Представления не хранят данные, а инкапсулируют типовые агрегаты. Это упрощает отчёты и не даёт приложению дублировать одни и те же `JOIN`/`GROUP BY`.

## 9. Транзакции, функции и триггеры

### 9.1. Явные транзакции

В `04_functions_triggers.sql` показаны обе операции:

- `COMMIT`: создаётся заказ пользователя 42 на товар 7 (2 шт. по 1500.00), остаток уменьшается с 17 до 15;
- `ROLLBACK`: остаток временно уменьшается на 1, затем транзакция откатывается, остаток остаётся 15.

### 9.2. Функция `place_order`

```sql
place_order(p_user BIGINT, p_product BIGINT, p_qty INT) RETURNS BIGINT
```

Функция:

1. проверяет, что количество больше нуля;
2. находит активный товар и его цену;
3. блокирует строку остатка через `SELECT ... FOR UPDATE`;
4. проверяет достаточность остатка;
5. создаёт заказ и позицию заказа;
6. уменьшает остаток и обновляет `stock.updated_at`;
7. возвращает номер заказа.

Блокировка `FOR UPDATE` защищает от одновременной продажи одного и того же остатка двумя транзакциями. Все действия выполняются в одной транзакции: при ошибке на любом шаге не остаётся «полузаказа».

### 9.3. Функция `seller_revenue`

```sql
seller_revenue(p_seller BIGINT, p_date_start DATE, p_date_end DATE)
RETURNS NUMERIC(12,2)
```

Считает выручку продавца за период. Конечная дата включается целиком:

```sql
AND o.created_at >= p_date_start
AND o.created_at < p_date_end + INTERVAL '1 day'
```

Если начальная дата позже конечной, функция выбрасывает исключение.

### 9.4. Триггер аудита цены

`trg_audit_product_price` срабатывает `AFTER UPDATE OF price ON products`. Если цена действительно изменилась (`IS DISTINCT FROM`), в `product_price_audit` пишутся старое и новое значения. Проверка `IS DISTINCT FROM` не создаёт записей при `UPDATE`, который не изменил цену.

Демонстрация: цена товара 7 меняется с 1459.00 на 1559.00, в аудите появляется одна запись.

### 9.5. Триггер рейтинга

`trg_refresh_product_rating` срабатывает `AFTER INSERT OR UPDATE OR DELETE ON reviews` и пересчитывает `products.rating` как `ROUND(AVG(score), 2)`. После добавления отзыва с оценкой 5 средняя оценка товара 7 становится 4.00.

### 9.6. Почему логика находится в БД

В базе данных размещена логика, которая отвечает за целостность и атомарность:

- проверка остатка и оформление заказа;
- аудит изменения цены;
- пересчёт рейтинга.

Такая логика должна работать одинаково для любого приложения: веб-интерфейса, мобильного клиента, скрипта импорта. Логика интерфейса и пользовательских сценариев остаётся на стороне приложения.

## 10. JSONB

Поле `products.attributes` хранит разнородные характеристики:

```json
{"color": "black", "memory": "256 GB", "screen": 6.4}
{"color": "silver", "ram": "16 GB", "storage": "512 GB"}
{"color": "black", "wireless": true, "battery_hours": 25}
```

Использованные операторы:

| Оператор | Смысл | Пример |
|---|---|---|
| `->` | Вернуть значение как `jsonb` | `attributes -> 'color'` → `"black"` |
| `->>` | Вернуть значение как `text` | `attributes ->> 'color'` → `black` |
| `@>` | Проверить вхождение JSONB | `attributes @> '{"color":"black"}'` |
| `?` | Проверить наличие ключа | `attributes ? 'memory'` |

Фактические результаты:

- товаров с `color = black` — 450 из 1000;
- товаров с ключом `memory` — 100 (телефоны).

JSONB выбран потому, что набор характеристик зависит от категории: у телефона есть память и экран, у клавиатуры — раскладка и тип переключателей, у наушников — время работы. Отдельные таблицы под каждый тип товара или EAV-схема усложнили бы выборки и сопровождение. При этом JSONB остаётся индексируемым через GIN.

## 11. Индексы и оптимизация

### 11.1. Выбранные индексы

| Индекс | Тип | Обоснование |
|---|---|---|
| `idx_products_category_price` | B-tree `(category_id, price)` | Равенство по категории + диапазон по цене + сортировка по цене |
| `idx_orders_created_at` | B-tree `(created_at)` | Отбор заказов за период |
| `idx_products_attributes` | GIN `(attributes)` | Поиск по JSONB через `@>` и `?` |

Составной индекс `(category_id, price)` работает по правилу левого префикса: он эффективен для условий `category_id = ... AND price BETWEEN ...`, но не заменяет отдельный индекс по одной цене.

### 11.2. Результаты `EXPLAIN ANALYZE`

Замеры выполнены на 1000 товарах и 1000 заказах, PostgreSQL 18.6. Время — `Execution Time` одного прогона; оно может колебаться, важнее устойчивость плана.

| Запрос | До индекса | После индекса |
|---|---|---|
| Товары категории 5 с ценой 500–3000 (27 строк) | `Seq Scan`, 0.064 мс | `Bitmap Index Scan` + `Bitmap Heap Scan`, 0.020 мс |
| Заказы за последние сутки (72 строки) | `Seq Scan`, 0.079 мс | `Bitmap Index Scan` + `Bitmap Heap Scan`, 0.012 мс |
| JSONB `color = black` (450 строк) | `Seq Scan`, 0.090 мс | `Seq Scan`, 0.090 мс; при `enable_seqscan = off` — `Bitmap Index Scan`, 0.066 мс |

### 11.3. Объяснение результатов

- **Товары по категории и цене.** До индекса PostgreSQL читает все 1000 строк и отбрасывает 973. После создания индекса выбирает 27 строк через bitmap-доступ. Ускорение в несколько раз (в зависимости от прогона — примерно в 2–3 раза).
- **Заказы за сутки.** До индекса читаются все 1000 строк, после — только 72. Ускорение в несколько раз (в зависимости от прогона — примерно в 3–6 раз).
- **JSONB.** Подходит 450 строк из 1000 (45%). Чтение половины таблицы последовательным сканированием дешевле, чем случайный доступ к половине страниц через индекс, поэтому планировщик оставляет `Seq Scan`. Это корректное решение, а не ошибка: GIN-индекс применим, что подтверждается принудительным `SET enable_seqscan = off` (0.066 мс). На больших объёмах и при более селективном условии индекс будет выбран естественно.
- **Стоимость поддержки.** Вставка 100 000 строк в таблицу без индекса заняла 16.113 мс, в таблицу с B-tree индексом — 43.418 мс. Индекс ускоряет чтение, но замедляет вставку и требует места, поэтому индексы создаются под конкретные запросы, а не «на все столбцы».

## 13. Обоснование ограничений целостности

- **Первичные ключи.** У каждой таблицы есть PK. В `order_items` и `cart_items` PK составной, потому что одна и та же позиция не должна дублироваться в одном заказе или корзине.
- **Внешние ключи.** Все связи между сущностями объявлены через FK. Это не позволяет создать товар у несуществующего продавца, заказ у несуществующего пользователя, позицию заказа без заказа и т.д.
- **`ON DELETE CASCADE`.** Используется для зависимых данных, которые не имеют смысла без родителя: адреса пользователя, корзина и её позиции, позиции заказа, платёж, доставка, отзывы, остаток товара, аудит цены.
- **`ON DELETE RESTRICT`.** Используется для справочных сущностей: нельзя удалить продавца, у которого есть товары; категорию, на которую ссылаются товары; пользователя, у которого есть заказы; адрес, используемый в доставке; товар, входящий в заказ. Это защищает историю заказов.
- **`UNIQUE`.** Гарантирует уникальность email и телефона, названия магазина, названия категории, а также одну корзину, один платёж и одну доставку на заказ. Пара `(user_id, product_id)` в `reviews` запрещает дубли отзывов.
- **`NOT NULL`.** Обязательные поля (имя, email, цена, количество, статус, сумма) не могут быть пустыми. Необязательными оставлены только реально необязательные: телефон, квартира, дата оплаты, дата доставки, рейтинг, JSONB.
- **`CHECK`.** Проверяет бизнес-правила: цена больше нуля, остаток неотрицателен, количество в заказе и корзине больше нуля, оценка от 1 до 5, рейтинг от 0 до 5, сумма заказа и платежа неотрицательна, статусы входят в допустимый набор.
- **Ограничение иерархии.** `CHECK (parent_id IS NULL OR parent_id <> id)` не позволяет категории быть родителем самой себе.

## 14. Подготовка к защите

**1. Почему схема считается находящейся в 3НФ?**  
Потому что все атрибуты атомарны, неключевые столбцы зависят от полного первичного ключа, а не от его части, и отсутствуют транзитивные зависимости: названия категорий и продавцов хранятся только в своих таблицах, а не дублируются в товарах.

**2. Зачем тогда `rating`, `total_amount` и `unit_price`, если их можно вычислить?**  
Это контролируемая денормализация. `rating` ускоряет чтение каталога и поддерживается триггером; `total_amount` и `unit_price` — снимки на момент заказа, которые сохраняют историческую стоимость при изменении цен. Если пересчитывать их из текущих цен, старые заказы изменятся.

**3. Почему `attributes` хранится в JSONB, а не в отдельной таблице?**  
Набор характеристик зависит от категории. JSONB позволяет хранить разные наборы в одном столбце, поддерживает операторы `->`, `->>`, `@>`, `?` и индексируется GIN. Отдельная EAV-таблица потребовала бы больше соединений и сложнее контролировалась бы.

**4. Чем `->` отличается от `->>`?**  
`->` возвращает значение типа `jsonb` (строка остаётся в кавычках), `->>` возвращает `text` без JSON-кавычек. Для сравнения с текстом удобнее `->>`.

**5. Что делает оператор `@>`?**  
Проверяет, содержит ли левый JSONB все пары ключ–значение из правого JSONB. Например, `attributes @> '{"color":"black"}'` истинно, если цвет чёрный, даже если есть другие ключи.

**6. Почему GIN-индекс не используется в обычном плане?**  
Условию удовлетворяют 450 строк из 1000 (45%). Последовательное чтение половины таблицы дешевле случайного доступа к половине страниц. При `enable_seqscan = off` видно, что индекс применим. На больших объёмах и при более селективном условии планировщик выберет его сам.

**7. Почему индекс составной `(category_id, price)`, а не два отдельных?**  
Запрос фильтрует по категории и диапазону цены. Составной индекс использует равенство по первому столбцу и диапазон по второму, а также может отдавать строки в порядке цены. Отдельный индекс по цене не использовал бы категорию, а отдельный по категории был бы менее точечным.

**8. Почему индекс по `orders.created_at` помогает?**  
Запрос выбирает только последние сутки из 14 дней. Индекс позволяет найти 72 строки, а не читать все 1000. Для отчётов по дням он также ускоряет диапазонные условия.

**9. Как `place_order` защищает от продажи одного остатка дважды?**  
Строка `stock` блокируется через `SELECT ... FOR UPDATE`. Вторая транзакция ждёт завершения первой и видит уже уменьшенный остаток. Если товара не хватает, функция выбрасывает исключение, и транзакция откатывается.

**10. Что будет, если товара не хватает?**  
Функция выбрасывает `Недостаточно товара на складе`; заказ и позиция не создаются, остаток не меняется. Это атомарность: либо всё, либо ничего.

**11. Чем `COMMIT` отличается от `ROLLBACK`?**  
`COMMIT` фиксирует изменения транзакции, `ROLLBACK` отменяет их. В работе показано: после `COMMIT` остаток 15, после `ROLLBACK` он остаётся 15, то есть временное уменьшение не сохранилось.

**12. Зачем нужен триггер аудита, если можно писать в лог из приложения?**  
Триггер срабатывает при любом изменении цены, независимо от приложения и способа изменения. Приложение можно обойти, триггер — нет. Проверка `IS DISTINCT FROM` исключает ложные записи.

**13. Как пересчитывается рейтинг?**  
Триггер после вставки, обновления или удаления отзыва берёт `product_id` из `NEW`/`OLD`, считает `AVG(score)` по отзывам товара и обновляет `products.rating` с округлением до двух знаков.

**14. Почему `total_amount` не пересчитывается автоматически при изменении `order_items`?**  
В текущей реализации сумма устанавливается функцией `place_order` и скриптом наполнения. Это осознанное ограничение: для production лучше добавить триггер на `order_items` или генерируемый столбец, иначе ручное изменение состава заказа может рассинхронизировать сумму. На защите это можно назвать направлением развития.

**15. Что произойдёт при удалении пользователя, у которого есть заказы?**  
Удаление будет запрещено (`ON DELETE RESTRICT` для `orders.user_id`), чтобы не потерять историю заказов. Если нужно удалять пользователя, сначала нужно решить судьбу его заказов (архивирование, анонимизация).

**16. Что произойдёт при удалении товара, который входит в заказ?**  
Удаление будет запрещено (`ON DELETE RESTRICT` для `order_items.product_id`): история заказа должна сохраниться. Для скрытия товара из каталога используется `is_active = false`, а не удаление.

**17. Чем `ROW_NUMBER`, `RANK` и `DENSE_RANK` отличаются?**  
`ROW_NUMBER` всегда даёт уникальный последовательный номер. `RANK` при равных значениях даёт одинаковый ранг и пропускает следующие номера. `DENSE_RANK` при равных значениях даёт одинаковый ранг без пропусков.

**18. Чем `LAG` отличается от `LEAD`?**  
`LAG` возвращает значение предыдущей строки окна, `LEAD` — следующей. У первой строки `LAG` равен `NULL`, у последней `LEAD` равен `NULL`.

**19. Почему даты заказов пришлось распределять?**  
Потому что `created_at` по умолчанию `now()`: все 1000 заказов получили бы одинаковую дату. Для анализа по дням, `LAG`/`LEAD` и накопительной выручки нужны разные даты. Распределение по 14 дням делает отчёты содержательными.

**20. Что показывает `EXPLAIN ANALYZE` и чем он отличается от `EXPLAIN`?**  
`EXPLAIN` строит план, но не выполняет запрос. `EXPLAIN ANALYZE` выполняет запрос и показывает фактические строки, время и число циклов. Поэтому для замеров использован `EXPLAIN ANALYZE`.

**21. Почему после создания индекса запрос всё равно может использовать `Seq Scan`?**  
Планировщик сравнивает стоимость вариантов. Если условие неселективно (например, 45% строк), последовательное чтение может быть дешевле индексного доступа. Это нормально; индекс всё равно нужен для более селективных запросов.

**22. Какие ограничения у проекта?**  
Нет аутентификации и хранения паролей; `total_amount` не поддерживается триггером; JSONB не валидируется по схеме; нет партиционирования и репликации; замеры выполнены на небольших объёмах (1000 строк), поэтому выводы об индексах нужно перепроверять на реальных объёмах.
